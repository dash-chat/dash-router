Dash Router

Nearby devices store and forward each other's messages until they reach their recipients.

Why Dash Router

When the internet is not available, we need a way to send messages through a mesh of phones until they reach their recipients.

Dash Router is our prototype of that. So far we've built its first routing protocol. It only works on a LAN, with the phones connected to each other. In the future we'd like to add more protocols and transports.

It's integrated in Dash Chat, a messenger that works without internet, and is built on p2panda.

The phones in between can't read your messages Dash Chat uses p2panda to encrypt messages with p2panda spaces before they leave your phone. A phone passing one along only ever holds encrypted data.

See it in Dash Chat

Try it yourself

Dash Router is in Dash Chat from version 0.23.1, but it's experimental and off by default. You need at least three devices on the same Wi-Fi or hotspot. On each one:

  1. Install Dash Chat from dashchat.org/download.
  2. Go to Settings › Help and tap Version seven times. A "Developer mode enabled" message shows up.
  3. Back in Settings there is now a Developer options entry. Open it and turn on Enable Dash Router.

You need at least three devices to really see Dash Router in action, because Dash Chat already makes it easy for any two devices to connect peer-to-peer. Dash Router is only useful when there are two devices that can't connect directly (e.g. because they're not connected to the network at the same time) and need one or more intermediaries to relay messages between them.

How it works right now

Conversations are append-only logs, one per author, so a device can describe everything it has for a conversation as a few ranges of sequence numbers. The protocol's two messages are built on that:

Want A list of what the sender already has. Anyone who has more is being asked to send the difference. A Want doesn't say who it came from.
Have Actual messages, sent because somebody's Want showed they were missing.

Every device runs the same few rules. There are three moments when it does something.

When it receives a message

  • A Want. Two things happen:
    1. It repeats the Want to everyone straight away, if it asks for anything that the Wants the device has seen in the last WANT_TTL don't already ask for. Otherwise the Want stops here.
    2. If the device holds something the Want is missing, and isn't already waiting to answer, it starts a timer of random length.
      • While the timer runs down, the device keeps listening to every Want and Have that goes by.
      • When the timer runs out, it works out what is still unanswered: everything the Wants it has seen ask for that it holds, minus what the Haves it has seen in the last HAVE_TTL already carried.
      • If anything is left, it sends that as a Have. As long as a recent Want still asks for something it holds, it starts the timer again.
  • A Have. Three things happen:
    1. It stores every message it doesn't have yet: with its own conversations if it takes part in that one, otherwise in its relay store, as long as there is room.
    2. It repeats to everyone the part of the Have it hasn't already repeated in the last HAVE_TTL, whether or not those messages were new to it.
    3. It remembers what the Have carried for HAVE_TTL, so that its own pending answer can leave that out.

On a timer that gets a new random length each time

  1. It lists every conversation it cares about, with what it already has for each: the ones it takes part in, the ones it holds messages for, and the ones it has recently heard another holder ask about.
  2. It removes every entry that the Wants it has seen in the last WANT_TTL, its own included, already cover, meaning they ask for everything that entry would.
  3. It sends a Want with the entries that are left. If none are left, it sends nothing.

When you write a message

Your device stores it, waits a moment, and sends it out as a Have. Everyone else treats it like any other Have.

The relay store has a size limit. Once a device hits it, it throws away the oldest message bodies first and keeps their headers, which are small.

This protocol enables the network to have these properties:

  • Multi-hop delivery. Messages get to devices that can't reach each other directly, without anyone knowing the route.
  • Delay tolerance. A device that was away, or missed a message, gets it later from whoever still has it.
  • Congestion control with less network traffic. A device doesn't send what it has already seen another device ask for or answer, so a request or a reply goes out once, not once per device.

How long the timers should be depends on how many devices are around and how many messages get lost. We're still tuning that, and it's what the simulations below are for. DESIGN.md has the full protocol.

Simulations

These are recordings of the protocol running in a simulator, in order of difficulty. Hit play or step through with the arrow buttons. Clicking a node shows its state.

  1. 1. A line of five Five devices in a row, one of them writing, nothing lost. Good for following a single message from one end to the other.
  2. 2. A lossy line of three A small but unreliable network: three devices in a row, with 30% of messages lost on the way. It heals itself when messages are lost.
  3. 3. A lossy network Twenty devices, four of them writing, and 15% of messages lost on the way.
  • Circles are devices. A device gets greener the more of the written messages it has, and its border flashes bright green when it writes one.
  • Each device has up to three small pies around it. The amber one is the countdown to its next Want. The blue one is the countdown to its next Have, and is only there while the device has something to answer. The green one shows how much of everything written so far it holds.
  • A link turns amber while a Want is crossing it and blue when a Have is. It flashes red when a message is lost on it.
